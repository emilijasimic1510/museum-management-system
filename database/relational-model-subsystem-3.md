# Relational model — subsystem 3

Sources: approved specification sections 4.3–4.6 and 5–12, and the subsystem 3 EER diagram. V1/V2 and the original approved documents remain unchanged.

Standalone IDs use bigint GENERATED BY DEFAULT AS IDENTITY; FKs use bigint, timestamps timestamptz (Instant), monetary values numeric(19,2), statuses varchar(32), and text fields text. Columns are NOT NULL unless explicitly optional. All FKs use ON DELETE RESTRICT ON UPDATE RESTRICT. Primary/unique keys and FKs are indexed.

The price FK is `(cenovnik_izlozba_id, cenovnik_vazi_od, kategorija_cene)` → `cenovnik_izlozbe(izlozba_id, datum_vazenja_od, kategorija)`. Route items use EmbeddedId/MapsId rather than an artificial ID.

CHECK sets retain the implemented enum identifiers:

- Ticket: KUPLJENA/AKTIVNA/ISKORISCENA/ISTEKLA/OTKAZANA.
- Transaction: POKRENUTA/USPESNA/NEUSPESNA/REFUNDIRANA; payment method KARTICA/GOTOVINA/DRUGO.
- Visit and route: AKTIVNA/ZAVRSENA.
- Route criterion: INTERESOVANJA/BLIZINA/POPULARNOST/KOMBINACIJA.
- Rating: 1..5; route position >= 1; optional viewing duration >= 0; exit time >= entry time; ticket expiry after purchase.
- Route explanation uses text and visited state uses boolean.

## Business rules and transactions

- The server chooses the price by category and purchase time within a half-open validity interval. When prices overlap, the latest validity start takes precedence. The paid amount is an immutable snapshot; later price edits do not change it. Payment retries select the price valid at retry time.
- Sales lock the admission-time row. Existing ticket updates lock the admission time before the ticket; scans and route operations lock the visit. Non-cancelled sales cannot exceed capacity. Database triggers also protect capacity reductions.
- Every ticket has at least one transaction at commit, enforced by a deferred trigger. A failed payment keeps an OTKAZANA ticket and NEUSPESNA transaction without occupying capacity; no additional pending-ticket status is introduced.
- Payment simulation is available only in local/test profiles and does not charge real cards. Other profiles disable payment until a real adapter is configured. The request field `demoDecline` is not a database column. An attempt starts as POKRENUTA; its outcome and ticket state commit atomically.
- QR tokens are cryptographically random and contain no personal data. Validation checks the token, expected admission time, successful payment, status, validity period, and one-visit-per-ticket rule. An activated ticket cannot be validated again.
- Only the ticket owner can use the visit's scanning and route operations. Cashiers can sell anonymous tickets and validate admission; anonymous sales do not create visitor profiles.
- Scans and route items must reference available participations in the visit's exhibition. Repeated scans are recorded; routes do not repeat participations. Ratings require a completed visit.
- History is preserved: these seven resources have no DELETE REST routes, and database rules prevent deletion. Cancelling an unused ticket marks payment REFUNDIRANA; the simulated adapter does not issue a real financial refund.
- Scheduled maintenance updates time-dependent states and closes expired visits/routes. Writes also check the current time independently of the scheduler.

## Recommendations and Neo4j

PostgreSQL remains the source of truth. Neo4j contains catalog identifiers and recommendation data, without accounts, email addresses, phone numbers, or payment transactions. The graph is a rebuildable projection of the catalog and aggregate exhibit transitions. Idempotent periodic synchronization supports recovery from PostgreSQL without an additional task table.

## REST contract

Private routes require JWT in every profile, including local. ADMINISTRATOR does not automatically inherit CASHIER permissions. Errors are 400 for validation, 401 for authentication, 403 for role/ownership, 404 for missing records, and 409 for business/database conflicts. A simulated purchase returns 201 when it creates a record even if payment fails; inspect ticket and transaction states.

Purchase input contains `termId`, `category`, `paymentMethod`, optional cashier `visitorId`, and the local simulation flag `demoDecline`. Price, status, timestamps, and QR token are computed by the server. Online purchases use KARTICA; counter sales also support GOTOVINA/DRUGO. Admission validation takes `qrToken` and `termId`. Route requests take `criterion`. Responses use DTOs, not serialized JPA entities.

## Graph projection and scheduling

`GraphProjection` creates `Eksponat`, `Izlozba`, and `Autor` nodes with `IZLOZEN_NA`, `AUTOR_JE`, and `CESTO_SLEDI` relationships. Theme/period information derives from existing `tip`/`godina_nastanka` fields rather than a new relational theme table. Interests match exhibit type text, which limits personalization to the available catalog data. Transitions are aggregated without exporting visitor or visit identities.

INTERESOVANJA scores interest matches; POPULARNOST scores transitions from the previous exhibit; KOMBINACIJA also considers shared authors and periods. BLIZINA uses differences in tour order as approximate proximity because no spatial coordinates exist. It is not precise indoor navigation. When personalization is unavailable, the curator order remains the fallback. Ties use deterministic curator order and ID. Routes exclude unavailable and already scanned participations.

`JourneyJobs` calls `JourneyMaintenance` and `GraphProjection` periodically, by default every 60 seconds. Changes become visible in the next projection cycle. There is no persistent outbox table or external message broker. Failed projections retry in subsequent cycles; restart recovery rereads PostgreSQL.

The current application includes a frontend and TTS added after the original subsystem phase. Real payment processing and fiscalization remain outside the implemented simulation. QR identifiers are generated and validated by the backend; the frontend renders QR images without adding a ticket image-path field to the schema.

Consent controls personalized recommendations. Missing consent, an unavailable graph, or insufficient graph data falls back to curator tour order. Recommendations are derived DTOs; persisted routes use the two approved route tables rather than a separate recommendation table.
